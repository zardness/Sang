RAG 성능 개선을 위한 메타데이터 활용 — 요점 정리
자료: ch09_12_RAG성능개선을 위한metadata활용(1).ipynb

1장 전체 목표와 처리 흐름
    -문서에 제목·카테고리·조항 정보를 추가하여 검색 범위를 좁히고 참고 조항을 표시하는 RAG 예제이다.
    -흐름: DOCX 읽기 → 청크 분할 → 메타데이터 생성 → CSV 백업 → Document 복원 → 임베딩·Pinecone 저장 → 필터 검색 → 답변과 참고 조항 출력.
    -메타데이터는 문서 본문을 설명하는 부가 정보이다.
    -성능 개선이 목적이지만, 개선 효과를 수치로 비교하는 평가 코드는 없다.

2장 문서 로드와 분할
    -Docx2txtLoader로 소득세법_with_markdown.docx를 읽는다.
    -RecursiveCharacterTextSplitter: chunk_size=1500, chunk_overlap=100.
    -문단 → 줄바꿈 → 공백 → 문자 순서로 분할을 시도한다.
    -chunk_size의 단위는 토큰이 아닌 문자이다.
    -각 Document는 본문 page_content와 부가 정보 metadata를 가진다.

3장 제목 추출과 텍스트 정리
    -remove_special_chars(): 줄바꿈을 공백으로 바꾸고, 지정한 문자 이외의 기호 및 중복 공백을 정리한다.
    -extract_title_with_llm(): 청크의 핵심 제목을 100토큰 이내로 작성하도록 모델에 요청한다.
    -주석에는 Ollama가 적혀 있지만 실제 활성 코드는 ChatUpstage의 solar-pro4를 사용한다.
    -정리된 텍스트로 제목을 만들며, Document의 본문에는 원래 content를 저장하려는 구조이다.
    -100토큰 이내는 프롬프트 요청이며 강제 출력 제한 설정은 아니다.

4장 카테고리 분류
    -처음에는 특정 키워드가 하나라도 포함되면 해당 카테고리를 선택하는 함수를 정의한다.
    -이후 같은 함수 이름을 가중치 기반 방식으로 다시 정의하므로 순서대로 실행하면 두 번째 함수가 사용된다.
    -get_category(): 납세의무·세율계산·근로소득·사업소득 등 14개 범주의 키워드와 가중치를 반환한다.
    -점수 계산: 키워드 출현 횟수 × 가중치를 카테고리별로 합산한다.
    -점수가 높은 범주부터 반환하고 top_k를 지정하면 상위 범주만 선택한다.
    -일치하는 키워드가 없으면 ['기타']를 반환한다.
    -기계학습 분류가 아닌 문자열 기반 규칙 분류이다. '거주자'와 '비거주자'처럼 포함 관계인 단어는 중복 집계될 수 있다.

5장 조항 추출과 메타데이터 구성
    -get_article(): 정규표현식 r"제(\d{1,3}조)"로 조항 번호를 찾는다.
    -중복 제거 후 숫자 순서로 정렬하여 '「9조, 60조」' 형태로 반환한다.
    -제10조의2 같은 세부 조항은 현재 패턴으로 구분되지 않는다.
    -metadata 구성:
        source   : 원본 문서 경로
        title    : 모델이 추출한 제목
        category : 분류된 카테고리 목록
        chunk_id : chunk_000 같은 청크 식별자
        article  : 본문에 등장하는 조항 번호
    -처리 반복문은 documents[:15]를 사용하므로 전체가 아닌 처음 15개 청크만 대상으로 한다.

6장 CSV 백업과 복원
    -Document 목록 → 딕셔너리 목록 → DataFrame → CSV 순서로 저장한다.
    -저장 파일: ./tex_docx/소득세법enhanced_chunks.csv
    -예제의 저장·읽기 인코딩은 cp949이다.
    -CSV에서는 category 리스트가 문자열이 되므로 ast.literal_eval로 다시 리스트로 변환한다.
    -복원 시 각 행을 Document로 만들고 article은 결측치가 아닐 때만 추가한다.
    -빈 목록을 저장하면 읽을 데이터가 없는 CSV가 생길 수 있으므로 저장 전 청크 수를 확인한다.

7장 임베딩과 Pinecone
    -UpstageEmbeddings를 사용하며 코드의 모델 설정은 embedding-query이다.
    -인덱스 이름: better-rag-index.
    -설정: cosine 유사도, AWS, us-east-1.
    -실제 인덱스 생성 차원은 len(embedding.embed_query("차원 확인용"))으로 계산한다.
    -기존 인덱스도 차원과 임베딩 모델의 호환성을 확인해야 한다.
    -전체 문서를 저장하는 from_documents 부분은 주석 처리되어 있고, 활성 코드는 기존 인덱스를 연결한다.
    -인덱스가 이미 있으면 첫 청크를 추가하는 코드가 실행된다. 반복 실행 시 중복 데이터가 생길 수 있다.
    -삭제 안내 문구와 달리 실제 삭제 호출은 없으므로 기존 데이터가 지워지는 것은 아니다.

8장 메타데이터 필터 검색
    -질문도 categorize_content()로 분류하여 문서의 category와 비교한다.
    -$in 조건: 질문의 카테고리 중 하나라도 해당하는 문서에서 유사도 검색을 시도한다.
    -$and 조건: 여러 카테고리 조건을 모두 만족하는 문서만 검색하도록 구성한다.
    -k는 가져올 문서 수이며, 예제에서는 4개 또는 3개를 사용한다.
    -검색 결과의 chunk_id, category, article, title을 출력하여 확인한다.
    -필터가 지나치게 좁으면 필요한 문서가 빠질 수 있다. '기타'로 분류된 질문도 검색 결과를 점검해야 한다.

9장 질문 표준화와 답변 생성
    -키워드 사전으로 일상 표현을 문서 검색에 사용할 표현으로 바꾼다.
    -예제: 직장인 → 근로소득이 있는 거주자, 세금 → 소득세.
    -keyword_chain = prompt | llm | StrOutputParser()
    -질문 변환과 최종 답변 생성에는 ChatOpenAI의 gpt-4o-mini를 사용한다.
    -retriever가 검색한 문서의 page_content를 format_documents()로 연결한다.
    -RAG 체인은 문맥·질문을 프롬프트에 넣어 모델 응답을 문자열로 반환한다.
    -final_chain = keyword_chain | rag_chain
    -사전 치환으로 원질문의 뜻이나 금액·단위가 달라지지 않는지 확인해야 한다.

10장 참고 조항을 포함하는 함수
    -extract_articles_from_docs(): 검색 문서의 article 정보를 모아 중복 제거·정렬 후 표시한다.
    -ask_with_reference(query, k=3)의 순서:
        ① 질문 표준화
        ② 표준화된 질문의 카테고리 계산
        ③ 해당 카테고리 필터를 사용하여 문서 검색
        ④ 검색 문서의 참고 조항 수집
        ⑤ 문맥을 전달하여 답변 생성
        ⑥ 원질문·표준화 질문·답변·참고 조항 출력
    -참고 조항은 검색 문서에 등장한 번호이다. 답변의 각 주장에 실제로 대응하는 근거인지 별도 확인이 필요하다.
    -함수는 결과를 출력하며 명시적인 return은 없다.

11장 코드에서 수정할 핵심 사항
    -enhanced_chunks로 초기화했지만 반복문은 enhanced_chunk.append()를 사용한다.
      append·길이 출력·이후 참조를 enhanced_chunks로 통일해야 한다.
    -metadata['article']에 get_article(content)를 넣은 뒤 이전 실습의 전역 article로 덮어쓰는 부분이 있다.
      if article: metadata['article'] = article 부분을 제거하여 현재 청크의 조항을 유지한다.
    -진행률에서 i/15*100에 다시 % 형식을 적용하므로 100배 크게 표시된다.
      {i/15:.1%}처럼 사용한다.
    -AND 검색 실습은 retriver로 생성하지만 retriever.invoke()로 실행한다.
      변수 이름을 통일해야 새로 만든 AND 필터가 사용된다.
    -final_chain의 필터는 retriever 생성 시점의 query로 고정된다.
      질문마다 필터를 다시 계산하는 ask_with_reference() 방식으로 구성하는 것이 필요하다.
    -참고 조항 정렬에서 '조항없음'이나 빈 문자열을 int()로 바꾸면 오류가 발생한다.
      유효한 조항만 먼저 골라낸 뒤 숫자 정렬을 수행한다.
    -documents[43] 조회는 청크가 44개 이상일 때 가능하다.
    -새 인덱스 생성 후 준비 상태를 확인하고, 전체 청크 저장 코드를 실행해야 검색할 데이터가 확보된다.

※ 첨부 코드의 내용과 실행 흐름을 요약했으며 외부 API 실행 및 성능 측정은 하지 않았다.
